Use this prompt in the EXISTING implementation workspace. The roadmap is not a request to recreate the app.

```text
Continue the existing Digital Kingdom implementation from the actual current
working state. Preserve the work already on main and any newer/uncommitted
work. Do not create a replacement app or replay the old rebuild program.

Read ROADMAP_FROM_MAIN.md, BACKLOG.json, CAPABILITY_GAP_MATRIX.json,
SURFACE_EXPANSION_MATRIX.json and CURRENT_MAIN_EVIDENCE.json in this package.
Read the repository's current agent, contribution and security instructions.

The reviewed baseline is 14d205fc295d0d8584f8c81d183193c4d75dc96d, but do NOT
reset the repository to it. Inspect branch, HEAD, working tree and concurrent
agent ownership. Diff newer work and reconcile completed requirements before
editing. Preserve unfamiliar changes and avoid competing writes.

The current product already includes the redesigned four workspaces, ten
architectural modules, event search, exact evidence retrieval, current-coverage
assessment, read-mostly MCP, ingestion hardening and browser tests. Reuse them.

First complete R00.1 as a current-state receipt. Then implement R00.2 as the
first bounded engineering slice: typed, namespaced event correlation. Reproduce
cross-source, cross-identifier-type, cross-asset and identifier-reuse cases with
failing tests; establish what correlation is explicitly supported; preserve
valid same-authority cases. Do not claim an end-to-end vulnerability reproduction
from source inspection alone. Review the corresponding route ambiguity in R00.3
and schedule its own bounded tests and fix.

Use the 52-package backlog as dependency-aware forward work. It is not an
instruction to implement all packages in one patch. Keep a requirement/status
ledger in the repository's existing tracking system. Each claim needs code and
actual execution evidence. Keep unrun, failed, externally blocked, implemented
and verified states distinct.

Preserve project authorization, issuer identity, source capabilities, redaction
before persistence, poison-record isolation, revision-aware evidence, synthetic/
live separation, current-versus-historical coverage, UI/MCP parity and immutable
historical evaluation records. No broad template swap or database/framework
replacement without a demonstrated requirement and compatible migration plan.

A rendering change must not change security truth. A received event is not
proof of impact. A query complete over stored data is not full visibility.
A provider contract test is not live-provider verification. A token called
human is not a verified independent approver. An approved action is not executed
or verified. Keep those boundaries explicit.

Run relevant targeted tests and then the required full checks on the candidate.
Inspect actual UI output for visual changes. Keep failed receipts. Do not skip
assertions or silently update visual baselines just to make checks green.

Paid model evaluation, provider spend, production credentials/actions, private
data transfer, merging, branch-policy changes and public deployment require
separate applicable approval. Use local synthetic scenarios and fake-model tests
by default. Read-only discovery still requires authorized scope.

At each checkpoint report the actual revision, reused components, changed files,
commands/results, evidence locations, remaining limitations, and next eligible
work package. Update persistent handoff files so the next session continues
without a restart. Complete implementation work, not another generic roadmap.
```
