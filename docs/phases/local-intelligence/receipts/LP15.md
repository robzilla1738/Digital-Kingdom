# LP15 — Create a local attention queue (receipt)

Milestone M3, branch `phase/li-m3` (worktree `DK-m3`). Depends on LP12 (workbench, CI-verified at `ca87929`).
Commit and CI run are recorded in STATUS.json (`packages[LP15]`).

Reused: the server's project-scoped change stream (`outbox`, already written for events, findings, sources, cases),
`Store.sourceState` (R01.2 last receipt per source), declared source freshness (`stale_after_seconds`), R03.1 cases
(scope assets/time window, linked findings), LP14 repair candidate sets (now also emitted to the change stream as
`repair_candidates` with ids and counts only) and LP13 `Exploration.baseline` (stale repair baselines), project
authorization (`store.require`), the audit log. The R03.5 notifier (`notify.ts`) is deliberately NOT used.

## What changed

- `apps/server/src/attention.ts` — `dk.attention_queue.v1` / `dk.attention_item.v1`:
  - Kinds: `new_evidence` (records stored after an open case was opened, on its assets and inside its time window;
    one item per case), `contradiction` (a finding with counterevidence; high when linked to an open case),
    `incomplete_repair` (repair candidates are plan-only and unverified by an executed check), `observer_gap` (a
    `sensor_unavailable` record or a disabled observer), `stale_check` (an enabled source past its freshness
    expectation; a case's repair set whose baseline has moved).
  - Deduplication: one item per (project, dedup_key). A distinct underlying record is an occurrence in the
    append-only `attention_log` (UPDATE/DELETE abort); the same record again (retried delivery, replayed stream) only
    increments `repeats`. The change-stream cursor (`attention_cursor`) is durable.
  - Acknowledgement: `POST /api/projects/:p/attention/:id/ack` (analyst; optional `expected_seq`, 409 when stale;
    any other field 422) marks the item acknowledged and records `attention.acknowledge` in the audit log — nothing
    else. A later distinct record reopens it with `new_since_acknowledged`.
  - Replay: `GET /api/projects/:p/attention/replay?after=<seq>` returns every queue change (raised, occurrence,
    reopened, acknowledged) in order; `GET /api/projects/:p/attention` (viewer) syncs then lists open /
    acknowledged / all items; `POST …/attention/sync`.
  - Bounded urgency: ceilings per kind (new_evidence medium, contradiction high, incomplete_repair medium,
    observer_gap high, stale_check medium); `critical` is never assigned; repeats never raise urgency; at most 5
    items per project become `high` in an hour, the rest are recorded `medium` with the reason.
  - Minimization: items carry kind, urgency, ids, counts, timestamps, recent source refs (`event:<id>`, …) and fixed
    template text; never titles, questions, notes, routes, attributes or evidence text.
  - Optional test sink: `AppConfig.attentionTestSink { url }` posts the same minimized items for newly raised or
    reopened items to a loopback URL only (`127.0.0.1`, `localhost`, `[::1]`; credentials refused; checked at
    startup). Off by default; not a notification destination.
- Migration `ATTENTION_MIGRATION` (additive); `hardening.test.ts` rewind drops the new tables.
- Console: `workspaces/investigate/AttentionPanel.tsx` at the top of Investigate → Cases: urgency, kind, counts,
  merged repeats, "new since acknowledged", Open case, Acknowledge (analyst/admin), and the statements that nothing
  is sent anywhere and acknowledging never closes a case or finding. `lib/attention.ts` re-filters a response to the
  current project.

## Limits

- The queue is computed when it is read or synced (bounded: 20 × 500 change-stream rows per call, then `behind:
  true`); there is no background worker. If the outbox is pruned past an unread cursor, those changes are not
  replayed into the queue (the records themselves stay stored); the state scan still catches staleness.
- Staleness of a source needs a declared `stale_after_seconds` and at least one received record.
- `new_evidence` is per case and counts records; it does not judge relevance. Urgency rules are fixed constants.
- No real remote delivery is exercised or claimed (R03.5 destinations remain gated by
  `authorized_notification_destination`). No model call; AI execution not exercised.
