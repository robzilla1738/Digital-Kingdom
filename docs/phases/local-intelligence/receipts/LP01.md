# LP01 — Repair scoped permission semantics (receipt)

Reused: R04.3 evaluator `apps/server/src/access/aws-policy.ts`, R04.4 change review, R03.3 credential aftermath,
`GET /access/paths` and MCP `dk_access_paths`. Nothing was replaced; the evaluator was corrected in place and its
decisions now carry `evaluator: "dk.aws_policy_eval.v2"`.

## Reproduction first

`apps/server/test/phase-lp01-permissions.test.ts` was written and run against the unmodified evaluator (commit
`9c0aec5`, source identical to `9fec7ed`). Result before the fix: see "Before" below (exact failing titles). The
defects reproduced:

- F01 (package finding): a conditional deny in a **permission boundary**, **session policy** or **SCP** was dropped from
  the final classification, so the decision was `feasible` instead of `conditional`; the same on a role-assumption hop.
- Resource globs were matched case-insensitively (`/public/*` granted `/PUBLIC/a.csv`; `/secret/*` denied `/Secret/x`).
- A resource with no `policy` key (unstated) was treated as "no policy" and could be `feasible`.
- `NotPrincipal`, policy variables and unknown statement keys were silently ignored (a `NotPrincipal` deny was skipped,
  giving `feasible`; an allow written with `${aws:username}` was dropped, giving a confident `blocked`).

## Repair (v2 precedence)

1. supported, unconditional, applicable explicit deny → `blocked` (unchanged);
2. any missing input (now including an unstated resource policy; `null` still means none) → `unresolved`;
3. an unsupported statement that may apply as a deny → `unresolved`; an implicit-deny result while an unsupported
   allow may apply → `unresolved` (never a confident block);
4. implicit deny in a required layer → `blocked`;
5. a conditional allow **or conditional deny in any layer** (identity, resource/trust, boundary, session, SCP) →
   `conditional`, with per-layer reasons, statement refs and condition keys;
6. otherwise `feasible`.

Actions match case-insensitively; Resource and principal ARNs case-sensitively. Every decision lists `unsupported`
statement refs and the declared limits in `not_claimed`.

## One authoritative result

- `GET /access/paths` returns `evaluator`, and each path's `decision` is exactly `evaluate()`'s object (deep-equal test).
- Change review (`reviewChange`) now returns `access_decisions[]` with base and candidate decisions per probe; the
  `broader_grant` change is derived from them (`blocked -> conditional` tested).
- Credential aftermath attaches `access_decision` to a surviving descendant key; its `surviving_permission` text is
  derived from that same decision (tested through real CloudTrail ingestion).
- MCP `dk_access_paths` returns the API decision unchanged (in-memory MCP client test).
- UI: no web surface renders access decisions today (`grep` of `apps/web/src` finds no access-path consumer), so there
  is no second interpretation to align. Recorded so a later UI package uses the API decision rather than re-deriving.
- Frozen evaluation records are untouched (LP00 digest test runs in the same suite).

## Compatibility

Existing R04.3/R04.4/R03.3 tests pass unchanged. The decision object gained `evaluator` and `unsupported` (additive).
A snapshot resource without a `policy` key now yields `unresolved` where v1 assumed none; all repository fixtures already
state `policy: null`. Permission boundaries that are omitted still mean "no boundary" (unchanged v1 semantics; a snapshot
exporter must use `"unknown"` when it could not read one) — recorded as a declared limit rather than changed silently.
