# LP22 — Verify effects independently (receipt)

Milestone M5, branch `phase/li-m5` (worktree `DK-m5`). Depends on LP21 (leased typed repairs) and LP07 (scenario
faults, private truth separation). Commit and CI run are recorded in STATUS.json (`packages[LP22]`).

Reused: LP06 `EffectObserver` (per-operation answers by supervisor-signed operation id, health intervals,
`unknown` across an outage), LP06 `probeOf` / `verificationReceipt` (`dk.local.verification_receipt.v1`: unknown ⇒
inconclusive, failed cleanup keeps overall from passing), the supervisor's monotonic clock, background `tick`, run
tokens and budgets, LP21 execution receipts and LP20 identity separation. The R08.4 server-side containment
verification (`apps/server/src/verification.ts`) is unchanged; this package verifies local runs, not the
production-facing path.

## What changed

- Contract `dk.local.repair_verification.v1` (`packages/contracts/schemas/local/repair-verification.v1.schema.json`,
  `validateRepairVerification` in `packages/contracts/src/lab.ts`): plan digest, execution state + receipt digest,
  verifier identity, independence block (`verifier_is_executor: false`, observers, basis), every observation
  (probe, repeat, operation id, nonce digest, observation digest, status, actual effect, observer, settled ms,
  reason), the baseline, residual access, disruption, security verdict, the embedded
  `dk.local.verification_receipt.v1`, cleanup and `whole_run` (`success`, `security_failed`, `inconclusive`,
  `execution_incomplete`, `cleanup_failed`, `cleanup_pending`, `refused`). Semantic checks: the embedded receipt is
  valid and agrees on verdict, run and cleanup; `success` only with a passing verdict, a completed execution and
  completed/unneeded cleanup; a pass is impossible with any unknown observation.
- `packages/local-world/src/runtime/effects.ts` — `EffectVerifier`:
  - its own identity: a run token with `request_route` + `read_effects`; a controller identity is refused, and a
    receipt whose controller is the verifier's own identity is refused (identities appear only as non-secret
    `ctl-…`/`vrf-…` references; the LP20 lease now carries `ctl-<16 hex>` too);
  - effects only from registered `observer` resources of the run, by operation id (`Run.observerAnswer`,
    read-only); probes naming the API or the ingress as "observer" are refused;
  - per probe and repeat: a fresh supervisor operation with a 128-bit nonce header (digest recorded), bounded
    settling on the monotonic clock (200 ms–5 s, background work ticked via `Run.settleFor`, early stop only when the
    effect is seen; absence is claimed only after the full window), observation digest over the correlated effects
    and outage reasons, evidence reference `obs-…`/`health-…`;
  - repeats (default 2, up to 5) as repeated health checks of the positive controls;
  - baseline comparison: unchanged prohibited behaviour after an accepted action is named; a baseline that never
    showed the prohibited effect, an unknown baseline or a positive control already broken before the repair cannot
    support a pass (downgraded to inconclusive);
  - residual access (prohibited effects still observed) and disruption (permitted operations refused or not
    observed) by probe; tested target revision checked against the executed revision;
  - security verdict, execution state and cleanup kept separate; `finalize()` re-reads the run's cleanup after the
    owner stopped and cleaned the run, from the observations already made.
- `supervisor.ts` (`Run`): `observerAnswer`, `settleFor`, `describeVerifier` (read-only verifier access);
  `Supervisor.describeToken`.

## Tests (executed) — `examples/reference-app/lp22-verify.test.ts`, 7 tests

- **LP22-A1** (2): in the weakened storefront the baseline shows the cross-tenant read; the wrong repair (ingress
  requires a session) is applied (`completed`, `ingress:policy-baseline-r1` → `candidate-r2`) but the
  session-carrying cross-tenant read is still 200 and observed by the audit observer → `fail`, residual access
  `cross-tenant-read`, "target behavior unchanged", whole run `security_failed`. The right repair (API back to
  baseline) → 403 and not observed while the own-tenant read is observed → `pass`, whole run `cleanup_pending`
  until the run is cleaned, then `success`. In a world without the defect the baseline never shows the effect →
  `inconclusive`; with no baseline the check is listed in `unassessed_paths`.
- **LP22-A2** (3): a cross-tenant JOB is accepted (202) and its effect lands later through the worker; it is
  attributed to the job's operation id (all effects carry it, `by: worker`, tenant-b) while concurrent tenant-b
  reads by tenant-b (recorded by the same observer under their own ids) are never attributed to a probe; after the
  repair, with the same concurrent noise, the job is 403 and not observed only after the full 1.5 s window, the
  own-tenant job's delayed effect is observed → `pass`; a 0 ms settle window is refused. With the audit observer
  stopped, every observation is `unknown` (the prohibited probe still got 403), every probe `inconclusive` /
  `unavailable`, verdict and whole run `inconclusive`. Independence: a controller token cannot be a verifier;
  probes using the API or the ingress as "observer" are refused; another plan's execution receipt, a receipt whose
  controller is the verifier, and a probe set without a positive control are refused.
- **LP22-A3** (1): removing the shared `read:deploy-data` grant blocks the leaked credential AND the legitimate one
  (403, not observed) → `fail`, disruption `legit-credential-read`, "is not a verified repair"; deactivating only the
  leaked token passes with three repeated health checks of the legitimate read.
- **LP22-A4** (1): a passing security assertion followed by a cleanup that fails (an outside hard link to the
  run-owned journal) → verdict `pass`, cleanup `failed` with the hard link named, whole run `cleanup_failed`
  (`success: false`), embedded receipt overall not `pass`; a forged `success` does not validate. A security effect
  achieved by a partially applied plan (quota) is `execution_incomplete`, not success.

Also re-run with LP22: LP20 (6), LP21 (9), `packages/local-world` (LP04/LP05), `phase-lp03-contracts`.

## Limits

- Observers are the run's built-in effect taps (LP06) in the same trusted process; their independence is by source
  identity, attachment and correlation, not OS isolation. A path that never reaches an observed resource is
  invisible and must be listed by the caller as unassessed (the queue and retrieval store have no observer).
- The nonce is recorded per probe but services do not echo it into effects; correlation is by the supervisor-signed
  operation id. Settling is bounded (≤ 5 s); effects slower than the window are reported as not observed only for
  that window.
- Local run only (`scope: local_run_only`); external effectiveness stays deferred (EXT01). No model call; AI
  execution not exercised.
