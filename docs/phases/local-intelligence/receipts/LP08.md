## What changed

- **Contracts adopted** (same method as LP03): `packages/contracts/schemas/local/investigation-contract.v1.schema.json`
  (`dk.local.investigation_contract.v1`) and `conclusion.v1.schema.json` (`dk.local.conclusion.v1`), adapted from the
  package proposals; precompiled into `src/generated/validators.js`; semantic validators, the shared
  `deriveReadiness` and types in `packages/contracts/src/investigation.ts` (exported from `@dk/contracts`).
  Adaptations: obligations carry `kind`, typed `target`, `basis` (which public input produced them),
  `supports_negative_claims`, `validity` (snapshot / source revisions / finding revision / digests) and
  `decided_at_revision`; the contract carries `derivation` (inputs list + `inputs_digest`),
  `negative_claim_requirements`, `closure_prerequisites`, `readiness_reason`; `run_id` is nullable (non-local
  projects); conclusions may carry an optional machine-checkable `predicate`. Proposal ids are rejected.
- **Server** `apps/server/src/investigation/contracts.ts` (`InvestigationContracts`): derivation from public inputs
  only (case scope, linked findings/events, declared asset kinds, applicable recipes, versioned obligation catalog
  `dk.obligation_catalog.v1`); append-only revisions and transition ledger (new tables + triggers, migration
  `INVESTIGATION_CONTRACTS_MIGRATION` in `investigation/schema.ts`); `applyResults` that accepts a result only when its
  scope equals the obligation's required scope; analyst inapplicability with documented reason; effective `view` that
  applies scope/evidence invalidations immediately without writing; `refresh` that records them as a new revision.
- `apps/server/src/investigation/conclusions.ts`: contract-level conclusion rules (`checkAgainstContract`) and the
  deterministic honest-unresolved draft (`draftUnresolvedConclusion`).
- Routes (`investigation/routes.ts`, registered from `app.ts`): `GET|POST /api/projects/:p/cases/:id/contract`,
  `GET …/contract/revisions`, `GET …/contract/revisions/:rev`, `GET …/contract/ledger`,
  `POST …/contract/obligations/:oid/inapplicable` (analyst, `expected_revision`, reason ≥ 10 chars),
  `GET …/contract/unresolved-draft`. Case update / item add / item remove refresh an existing contract
  (`afterCaseChange`). `/api/capabilities` lists `contracts.investigation`.
- `apps/server/test/hardening.test.ts`: the v0.2 rewind drops the three new tables (required for every new migration).

## Limits

- Obligations are filled by LP09 jobs; in this package the tests produce real results with the existing search and
  coverage services and apply them through `applyResults`.
- The obligation catalog decides which event classes make a negative claim meaningful per declared asset kind
  (at most two per kind). It is public and versioned but coarse; a case cannot yet request an extra class.
- Evidence-change detection for coverage uses source configuration revisions and late arrivals on the asset; a
  retention purge that changes historical liveness without either is not detected.
- Case questions/hypotheses are closure prerequisites (analyst-settled), not obligations: telemetry cannot settle
  intent or authorization.
