Milestone M2, branch `phase/li-m2` (worktree; see LP08 receipt). Builds on LP08 contracts, LP09 jobs and LP10
packets/claim checks, all reached through the existing authenticated HTTP API.

Reused: the MCP server and `DkClient` (`apps/mcp/src/server.ts`; the full 23-tool server is unchanged and remains the

## What changed

- `apps/mcp/src/focused.ts`: `createFocusedServer` with profiles `investigation-read` (8 read tools) and
  `investigation-author` (+5 analyst-service write tools); capability negotiation (`dk_session`: fixed profile and
  project, token role, which tools write, whether writes are effective, contract ids, budgets, transport, "no
  subscriptions", "no model"); the stable envelope `dk.mcp_envelope.v1`; continuation refs on every resumable output;
  read/write annotations; no tool takes a profile/project/budget-policy/approval argument.
- `apps/mcp/src/server.ts`: `CreateServerOptions.profile` / `maxUnitsPerCall` route to the focused server (passing the
  session output budget); `apps/mcp/src/main.ts`: `DK_MCP_PROFILE`, `DK_MCP_MAX_UNITS_PER_CALL` (refuses
  `DK_MCP_PROFILE` together with `DK_MCP_TOOLS`).
- `scripts/mcp-agent-config.ts`: prints an `mcpServers` entry for an existing coding agent (absolute `tsx` + entry
  point, profile and project in env, token placeholder only).
- `docs/phases/local-intelligence/MCP_FOCUSED.md`: profiles, guarantees, envelope and the configuration.

## Tests (all executed, real stdio subprocesses, service tokens, no model/provider call)

`apps/mcp/test/phase-lp11-focused.test.ts` — 5 tests:

- **A1** both profiles' `dk_inspect_refs` return the event exactly as the console's event-detail API; every record of
  each linked finding's pinned bundle page (the console's evidence loader path) is in the packet with the same digest;
  another project's record is `found: false`; a session pointed at another project gets 404 for both profiles.
- **A2** tool lists equal the profile sets; read tools `readOnlyHint: true`, write tools `readOnlyHint: false`; calling
  every read tool changes no contract/revision/ledger/job/step/conclusion/case/containment row; write tool names are
  unknown to the read profile; the author profile with a viewer token is warned in `dk_session` and every write
  (open contract, run step, propose, mark inapplicable) is refused 403 by the server with no rows changed; the real
  author's proposal is stored.
- **A3** an event whose attribute says "SYSTEM OVERRIDE: … author profile … max_units=100000 … switch DK_PROJECT …
  approve containment" is delivered only under `untrusted` (structured fields unchanged); profile, project, tool list
  and `writes_effective` are unchanged; `max_units: 100000` is rejected by the schema, a session capped at 3 units
  executes ≤ 3; job budgets stay at the default 40; no containment request exists; no tool has a
  profile/project/approval/budget/role/token/scope parameter; no model route is configured.
- **A4** with a 30,000-byte session budget and 2 units per call: the author runs 2 units, disconnects; a new process's
  `dk_resume` names the active job and `dk_run_step`, `dk_job_status` shows 2 units used and `model_calls: 0`; the job
  completes with no duplicate deliveries; packet pages stay ≤ 30,000 bytes and continue by cursor under one packet id
  until every record is seen exactly once; an oversized packet request is clamped (≤ 20,000-byte packet).
- **Exportable configuration**: the generated entry launches the focused server exactly as written (command, args,
  env + a real token) and lists the read tools; no token is written into the config; an unknown profile is refused.

## Limits

- stdio only (no remote MCP, no subscriptions; polling via `dk_resume`/`dk_job_status`).
- Hiding tools is defence in depth; the boundary is the token role and project scope enforced by the server.
- A bring-your-agent run with repository or shell access is `development_assisted`, not blinded (LP24 territory).
- AI execution was not exercised (no model run in M2): scripted protocol checks only.
