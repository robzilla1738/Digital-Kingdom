Reused: R03.2 recipes (`apps/server/src/recipes.ts`, corrected in place), R01.5 bounded search and signed cursors
(`investigate.ts`, unchanged), R01.2 historical coverage (`coverage-history.ts`, unchanged), R00.2 typed namespaced

## Reproduction first

passed (the zero-observer case was already handled by historical coverage). A separate probe against recipes@1
recorded the old behaviour (verbatim output):

```
A3 partner-ns: guessing_succeeded supported contains decisive: true
A1 budget=1: conclusion_allowed true false:Authentication was observable. | false:Data access was observable afterwards.
A1 no data store: true Authentication was observable. | Data access was observable afterwards.

```

i.e. (F02) budget exhaustion and a graph without data stores read as "observable"; a truncated follow-on search
still allowed a conclusion; the same raw `actor_ref` from an unrelated identity authority supported the hypothesis;
failures + success + ordinary activity "supported" credential guessing; a corroborated allowed call "supported"
"the result of a reported, allowed tool call" with no separate approval hypothesis.

## Repair: recipes@2, `dk.recipe_run.v2`

- **Obligations**: every query and coverage question is an obligation with status `satisfied | partial |
  unavailable | failed | not_started | inapplicable_with_reason` and a reason. `completeness` is `partial` while any
  obligation is unfinished; `conclusion_allowed` requires no triggered stop condition AND every obligation satisfied.
- **Explicit unknowns**: a coverage question the budget never reached is `not_run` and triggers its stop condition;
  a coverage failure is `failed`; zero capable sources is `unavailable`; a graph with no data store records the read
  question `unavailable` ("no conclusion about data access is possible"). No stop reason can say "observable" unless
  the coverage answer was actually `covered`.
- **Paging**: queries follow signed `next_cursor` pages within the budget (budget unit = one page or one coverage
  question, max 12). A query cut by the budget is `partial` with `continuation: { params, cursor }` in
  `outstanding`; a failing page is `failed` with the error, never an empty result or a 500.
- **Namespaces**: actor/session/run pivots carry `scope: { type, namespace, value }`; results whose correlation
  identity differs (different declared namespace, or undeclared per-source namespace) go to
  `other_authority_event_ids` and never into support.
- **Observable vs intent/approval**: hypotheses carry `kind`. Auth recipe: `failures_then_success_same_identity`
  (observable, may be `supported`), `credential_guessing` and `legitimate_mistyping` (intent; never supported, no
  supporting ids). Agent recipe: `effect_matches_allowed_call` (observable), `call_was_approved` (authorization; never
  supported), `bypass`. Blocked-request and change recipes mark authorization hypotheses explicitly and their stop
  condition now triggers when the allowed-request search is incomplete.

## Interfaces kept consistent

- `POST /recipes/:id/run` (and MCP `dk_run_recipe`, same body) returns v2; `/api/capabilities` reports
  `recipe_run: dk.recipe_run.v2` and `…@2` ids. Case attachment labels each hypothesis with its kind and lists
  outstanding work in the attached note.
- Web: `RecipeRun` type gains optional `kind`, `completeness`, `outstanding`; the Cases recipe runner shows an
  "Incomplete: N outstanding" warning list and each hypothesis kind (v1-shaped results still render).

## Limits

The budget is still small by design (default 6 units); a high-volume pivot will commonly end `partial` with a cursor,
which is the intended honest outcome. Recipes do not resume a continuation themselves; the cursor is usable with the
event search API (same params) until it expires (60 min).
