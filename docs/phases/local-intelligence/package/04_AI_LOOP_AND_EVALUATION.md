# AI loop, private truth, and evaluation contract

## 1. Objective

Use AI to exercise the real Digital Kingdom workflow without connecting third-party infrastructure. Test the investigation, comparison, local action, and verification loop. Do not turn this phase into an assertion that synthetic success proves real-world effectiveness.

This is a new evaluation track. The earlier v1/v2 artifacts and pending review records remain byte-for-byte preserved unless a separately authorized annotation is appended in a new location. Do not reuse old results as evidence of the new workflow.

## 2. Separate actors and authority

| Actor | Reads | Can change | Cannot access |
|---|---|---|---|
| World builder | Reviewed blueprint and catalog | Disposable run-owned services under supervisor policy | Production/cloud accounts, host files outside manifest |
| Stimulus runner | Finite scenario actions | Synthetic state through allowed local operations | Application source or investigator policy at will |
| Observer | Specific local effects and health | Its own append-only observations | Approvals, conclusions, scenario grading |
| Investigator | Authorized product API/MCP and public task | Scoped case drafts when analyst-service authority exists | Private truth, hidden seed, arbitrary shell, executor lease |
| Repair author | Public case, baseline, approved templates | Candidate patch in a disposable branch | Baseline/live environment, provider credentials |
| Controller | Exact plan and supervisor lease | Registered local targets only | Unbounded instructions from evidence/model text |
| Product verifier | Target state and admissible independent observations | Verification result | Private grading truth |
| Private referee | Scenario truth plus actual observations and trace | Score/result records | Product conclusions or evidence during an attempt |
| Optional AI reviewer | Bounded output/evidence bundle | Advisory semantic critique | Human approval status or grading truth used as a product input |

Several roles may use the same model binary, but they require separate conversations, stores, credentials and capabilities. Calling a second model does not by itself make the check independent. Sharing the product’s expected-result helper with the referee defeats independent verification.

## 3. Three execution modes

### Scripted

No LLM is involved. A deterministic client exercises real HTTP/MCP, pagination, cases, plans, actions and observed effects. This verifies engineering contracts and gives a stable baseline. It must be labeled scripted.

### Bring your current agent

The owner’s current AI connects through a local scoped MCP profile and receives a task from the run controller. It should not use arbitrary shell to inspect fixtures or call application databases. Record all capabilities it actually had.

A coding agent may already have seen implementation and expected fixtures. Such a run is `development_assisted`, not blinded held-out research. It can still reveal broken workflows and be a useful acceptance exercise. For blinded tests, start a fresh restricted driver with no oracle mounts and no repository/file tools, or explicitly report that isolation was not available.

### Approved model adapter

Use an already available local model endpoint or separately approved remote route. Pin model ID, prompt, decoding configuration, tool schema, budget and timeout. Reserve worst-case cost before a request; cancel requests on timeout; account for in-flight requests. Do not inherit previous authorization or silently switch providers.

No raw provider token is sent to the UI, an exported capsule, an investigator response, or a log. Synthetic evidence still needs minimization. The model broker cannot become a general outbound proxy for the stimulus engine.

## 4. Public task versus hidden scenario

A public task can say: “Determine whether the observed account activity was followed by a data read, whether you can attribute it to the same principal, and what access remains.” It may define the desired scope and an allowed response class.

It must not say: “Find event 217, which proves the attacker used the child token.” The existence and meaning of event 217 may be precisely what the investigation must establish.

The private scenario stores controlled operations, actual state changes, observer behavior, acceptable answer predicates, and repair goals. It is not served by product APIs or indexed in case search. Filenames, seeds, directory names, event labels, hidden goal IDs and scene layout must not encode the answer.

Generate distinct public inventory/evidence and private oracle files. A deliberate canary string placed only in the private oracle can detect accidental exposure. This cannot prove that no leakage occurred, but a hit must invalidate the affected blinded result.

## 5. Admissible truth

There are two truths to grade:

- **World truth:** what controlled operation occurred.
- **Admissible conclusion:** what the investigator could reasonably establish from its authorized evidence.

If a read happened while every suitable observer was down, the correct admissible answer may be “unknown.” Penalizing that answer would train the model toward fabrication. Conversely, if the record was reachable and the agent failed to retrieve it, record retrieval failure even when the answer says unknown.

The referee derives expected world state from separate action receipts/resource snapshots. It derives admissibility from intentionally configured source capabilities and delivery state. Do not obtain the expected verdict by running the same Digital Kingdom detection or policy helper being assessed.

For a policy model, construct finite truth tables or independently specified cases covering the supported semantic subset. These prove local behavior, not full provider equivalence.

## 6. Run manifest

Record source commit and dirty state; lockfile and compiled schema hashes; run, project, blueprint, scenario and seed commitment; runtime versions; model route; tools and authorization; observation coverage; request and query budgets; event and wall clocks; UI/API/MCP bundle revisions; and approval/lease state.

The manifest declares `scripted`, `development_assisted`, or `restricted_model`. It also declares `fixture_delivery`, `observed_local_runtime`, or a mixture whose components are individually labeled.

A synthetic-data local source may still use the repository’s existing live-ingestion semantics because actual local operations are being observed. Do not repurpose dataset_kind to claim external production use. Add explicit run/environment provenance through versioned contracts.

## 7. Investigation protocol

1. Validate capability and resource isolation; refuse invalid targets before stimulus.
2. Start registered sources and verify the necessary observer paths.
3. Materialize the scenario and independent truth store.
4. Present identical permitted inventory, clock and source metadata to compared conditions.
5. Start a fresh investigator session. Open the case contract through normal authority checks.
6. Record every tool request, delivered record and continuation. Preserve budgets/errors.
7. Accept a structured conclusion containing observed propositions, evidence references, uncertainty and candidate action classes.
8. Run deterministic evidence/obligation checks. Do not transform failed checks into a claim of correctness because prose sounds convincing.
9. For repair scenarios, isolate plan/lease/controller actions, then perform independent positive and negative checks.
10. Seal run results and cleanup status. Only then allow debrief/truth access.

The product workflow may tell an agent that an evidence obligation is unresolved. It must not consult hidden scenario requirements or expected IDs to provide that hint.

## 8. Comparison conditions

Use the same underlying normalized records, source configuration, inventory and interval. Preflight reachability for each tool condition using the actual scoped identity. Report preflight invalidity separately.

Compare:

- Existing full-tool investigation profile.
- Existing event-tools-with-context profile, accurately described (it already returns coverage and finding references).
- Guided investigation-contract profile.

A raw bundle can be an additional comparison if it fits without truncation, but it changes retrieval effort and context placement. Do not describe the experiment as isolating all information effects.

Choose question, prompt, call/token/query limits, held-out generators, variant ordering and primary metrics before running. Interleave conditions and clean/injected twins with a committed schedule. Keep provider/model changes from silently spanning one comparison block.

A deterministic development-only planner may retrieve records automatically. Report its work and cost as part of the guided system; do not count that retrieval as independent model skill.

## 9. Metrics and denominators

| Metric | Numerator / denominator | Caveat |
|---|---|---|
| Environment execution | Locally executed valid scenarios / eligible attempted scenarios | Not model quality |
| Evidence reachability | Required admissible items retrievable / all required admissible items | Preflight capability |
| Retrieval | Required items exposed to investigator / reachable required items | Exposure is not attention |
| Structured conclusion | Correct mechanically judgeable predicates / eligible predicates | No arbitrary prose approval |
| Claim validity | Scoped available references and obligations passed / submitted claims | ID validity is not semantic entailment |
| Repair selection | Candidate satisfies objective and constraints / eligible repair tasks | Multiple acceptable candidates allowed |
| Verified repair | Negative and positive tests plus residual checks pass / started repair attempts | Missing observer is inconclusive |
| Collateral disruption | Permitted controls broken / repair attempts | Must accompany success metric |
| End-to-end local success | All required task predicates pass / all valid started attempts | Failed retrieval and budgets count |
| Cost and effort | Calls, tokens, query pages, elapsed time and bytes | Scripted/planner work included |

If semantic grading is deferred, label it `ai_reviewed_advisory` or `unreviewed`. No zero-failure result becomes immunity. A review packet is not an approval.

## 10. Variants and mutation checks

Every selected family needs a benign alternate, missing-evidence variant and noisy/renamed variant. Injection families use matched neutral text and imperative text in an untrusted evidence field; record clean-repeat variation separately.

Mutation checks must detect at least these broken implementations: missing conditional-deny propagation, raw-string identity joins, a recipe that stops at page one, null coverage treated as healthy, an API ACK treated as verified effect, a self-report counted as independent, an agent able to create its own lease, and a capsule exposing private oracle data.

Do not generate arbitrary exploits. A controlled action behind a deliberately weak synthetic policy and a separate receiver can test the relevant defense behavior without offensive tooling.

## 11. Deferred human and external validation

The owner does not need to recruit users or connect real accounts to finish this phase. Retain those future gates in a separate ledger. They are not hidden dependencies for local acceptance.

Later human review can assess narrative nuance, usable interaction and visual comprehension. Later provider tests can assess actual provider semantics and deployment costs. Neither may be replaced by an AI declaring them passed.

## 12. Exit evidence

Provide scripted run receipts, real MCP transport logs, actual browser captures, objective scoring output, optional actual model-run manifest, failed/partial records, controlled isolation checks, and a list of what remains deferred. Publish a compact comparison only for dimensions actually measured.
